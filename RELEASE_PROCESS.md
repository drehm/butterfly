# Release Process for Butterfly

This guide documents the steps needed to release a new version of the Butterfly application.

## Prerequisites

- Maven installed (or use `mvnw.cmd` wrapper)
- Git repository up-to-date
- `gh` CLI installed and authenticated
- All code changes committed to git

## Release Steps

### Step 1: Update Version in pom.xml

Edit `pom.xml` and update the version number:

```xml
<version>X.Y.Z</version>
```

Example versions:
- `0.0.0.1` → `0.0.0.2` (patch)
- `0.0.0.2` → `0.1.0` (minor)
- `0.1.0` → `1.0.0` (major)

The version automatically syncs to `Main.java` via Maven resource filtering.

### Step 2: Commit Version Change

```bash
git add pom.xml
git commit -m "Bump version to X.Y.Z

Co-authored-by: Copilot <223556219+Copilot@users.noreply.github.com>"
git push
```

### Step 3: Build the Application

Clean build with Maven:

```bash
mvn clean package -DskipTests
```

This creates:
- `target/butterfly-X.Y.Z.jar` (executable JAR)
- `target/classes/app.properties` (with injected version)

Verify the build succeeded with no errors.

### Step 4: Create GitHub Release

Create a release tag and upload the JAR:

```bash
# Create the release with tag vX.Y.Z
gh release create vX.Y.Z \
  --title "vX.Y.Z" \
  --notes "Release notes describing changes" \
  target/butterfly-X.Y.Z.jar
```

Or without release notes:

```bash
gh release create vX.Y.Z target/butterfly-X.Y.Z.jar
```

### Step 5: Verify the Release

Check that the release is available:

```bash
gh release view vX.Y.Z
```

Should show:
- ✓ Tag name: `vX.Y.Z`
- ✓ Asset: `butterfly-X.Y.Z.jar`
- ✓ Status: Published

## Full Command Sequence

Here's the complete command sequence to copy/paste (replace X.Y.Z with your version):

```bash
# 1. Update pom.xml version (manual edit or script)
$version = "X.Y.Z"

# 2. Build
mvn clean package -DskipTests

# 3. Create release
gh release create v$version `
  --title "v$version" `
  --notes "Release notes here" `
  target/butterfly-$version.jar

# 4. Verify
gh release view v$version
```

## Auto-Update Testing

After release, the auto-update feature will check GitHub for new versions:

1. Users with older versions will see "Update available"
2. The app downloads the new JAR from the GitHub release
3. Users can install the update (when UI prompts them)

Test this locally:

```bash
java -cp "target/classes" com.weareplanet.butterfly.Main
```

(Current version must be older than the released version to trigger update check)

## Troubleshooting

### Build fails
- Ensure no syntax errors in code
- Run: `mvn clean compile` to see detailed errors
- Check Java version: `java -version` (should be 8+)

### Release creation fails
- Verify `gh` is authenticated: `gh auth status`
- Check repo is public: `gh repo view drehm/butterfly --json visibility`
- Ensure JAR file exists: `ls target/butterfly-*.jar`

### Version mismatch in app
- Version loads from `target/classes/app.properties` (generated by Maven)
- If outdated, run: `mvn clean` then rebuild
- Clear IDE caches if using IDE

## Implementation Details

**How version sync works:**

1. `pom.xml` contains `<version>X.Y.Z</version>`
2. Maven resource filtering processes `src/main/resources/app.properties`
3. Placeholder `${project.version}` is replaced with actual version
4. `Main.java` loads version from `app.properties` at startup
5. `UpdateChecker` uses this version to check for newer releases

**Why this approach:**

- ✓ Single source of truth (pom.xml)
- ✓ Automatic sync, no manual updates needed
- ✓ Works with CI/CD pipelines
- ✓ JAR filename matches version automatically
- ✓ UpdateChecker always has correct current version
